# Kubernetes recovery audit, 17 September 2026

The cluster recovered on its original single `Standard_B2ms` node. At 19:47 UTC all 43 Deployment, one StatefulSet and 20 DaemonSet readiness checks passed, and all seven Longhorn volumes were attached and healthy. PostgreSQL, both Redis services and cluster DNS had ready endpoints. The Azure userpool had one node, autoscaling enabled, and minimum and maximum counts both set to one. A subsequent Telegram application error exposed a closed client inside an otherwise Running pod; its connection was recovered at 19:57 UTC as described below.

A temporary second node was used during recovery and then drained and deleted. Its temporary usage can appear on the Azure bill. No second node remains. The existing zero-node support pool was left unchanged. Terraform's node counts remain one.

## What caused the failures

### Memory pressure and PostgreSQL connections

The initial audit found hundreds of failed pods, widespread unavailable controllers, and memory evictions. Available memory within the pod allocation fell to roughly 35–70 MiB, below the 100 MiB eviction threshold. Host memory pressure averaged roughly 88% over a minute, with severe I/O stalls. Disk space exhaustion and exhausted Azure CPU credits were not supported by the measurements.

PostgreSQL used about 3.1 GiB despite a small database footprint. Two server processes accounted for most of that memory. Its ten client sessions were idle, with no active transactions observed. A rolling restart of the backend using the already deployed image released these connections. PostgreSQL memory fell to about 125 MiB without restarting PostgreSQL. This establishes that memory retained by those connections materially contributed to the incident. The exact allocation mechanism has not been established.

After recovery, the node reported about 2.25 GiB available memory, and the pod allocation had about 1.18 GiB available during backups. Memory pressure fell sharply. At the final readiness check, the node reported neither MemoryPressure nor DiskPressure. These are short observation windows, not a guarantee that the application cannot accumulate memory again.

PostgreSQL and MariaDB use Azure Disk CSI volumes. Their storage is separate from Longhorn. Kubernetes documents how node memory pressure causes [pod eviction](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/).

### Multipath claimed Longhorn disks

Once memory pressure subsided, Grafana, InfluxDB and Uptime Kuma still failed to mount their volumes. The host's multipath service had claimed four Longhorn iSCSI devices. The resulting device-mapper maps prevented CSI from mounting the underlying devices normally.

Each affected map was checked against its volume, device identity and zero open-user count. The Longhorn devices identified themselves as vendor `IET`, product `VIRTUAL-DISK`. Azure disks had different identities. The existing `/etc/multipath.conf` was backed up to `/etc/multipath.conf.before-longhorn-fix-20260917`, then this narrow exclusion was added:

```conf
blacklist {
    device {
        vendor "^IET$"
        product "^VIRTUAL-DISK$"
    }
}
```

The configuration parsed successfully, and a multipath dry run confirmed that a verified Longhorn device was excluded. Reconfiguration released the unused maps; a targeted flush also completed successfully. CSI retries then mounted the existing filesystems and the affected applications became ready. The final check found no remaining device-mapper maps.

This is a documented [Longhorn and multipath conflict](https://longhorn.io/kb/troubleshooting-volume-with-multipath/). The exclusion here uses the observed vendor and product identities rather than broadly excluding every `sd*` disk. Device exclusions and map removal are described in [Red Hat's multipath documentation](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html-single/configuring_device_mapper_multipath/index).

The host configuration survives a reboot of this VM. The accompanying module change automates it for replacement nodes; that change has not yet been applied.

### Redis configuration and reconnection

Shared Redis requested three Longhorn replicas on a one-node cluster. It had one running, healthy replica. The desired count was changed to one after confirming that replica and its engine connection. No replica was deleted.

Its backup target pointed to the unconfigured `default` target. It now uses the existing working `azblob` target. Both Redis instances loaded their persistence files and reported successful persistence status. Shared Redis's AOF was only 88 bytes; this audit cannot establish whether that small dataset matches historical expectations.

The deployed backend stopped retrying Redis after three failed attempts. A final rolling restart after Redis recovered restored its Redis connection. Database connection success was also observed in the backend logs.

## Changes applied

| Change | Result and limits |
| --- | --- |
| Recycled backend connections with rolling restarts | Released PostgreSQL memory; preserved the PostgreSQL process and data volume. The connection lifecycle still needs an application fix. |
| Pinned the backend to its existing image digest during recovery | Avoided accidentally deploying a different `latest` image. No application code was deployed. |
| Restored unavailable DNS, connectivity, metrics, Argo and Longhorn CSI controllers | Used controller restarts or reviewed pod evictions. No manual restart of volume engines or database pods. |

| Set shared Redis's desired replica count to one and target to `azblob` | Matched the one-node design and enabled its backup. |
| Ran the existing daily Longhorn backup job once | All seven individual backup records completed at 100%, with no recorded error. Existing retention of three backups remained in effect and retired older backups normally. |
| Drained and deleted the temporary node | Verified it held no Longhorn replicas, engines or remaining volume attachments before deletion. Userpool count/minimum/maximum returned to one. |

## Telegram bot follow-up at 19:57 UTC

The user reported `The client is closed` from `AutoModerationStack.multichatSpamHandler`, specifically its Redis `rPush` call. The bot pod had remained Running throughout the Redis outage and had no readiness probe to detect this application failure.

The deployed bot and the local source used a reconnect policy that returned `false` after three startup failures or five failures following a successful connection. That permanently closed the shared client. A separate read-only Redis connection from inside the bot pod returned PONG, ruling out a continuing reachability failure.

Two regression tests exercised the real installed Redis client and the application's connection configuration against a local TCP test server. Both reproduced the exact `The client is closed` exception when Redis returned after the retry budget had expired. The source fix keeps reconnecting with a delay capped at two seconds plus jitter. Both regressions then passed, along with all 165 tests (including the subsequent worker recovery tests), type checking, formatting checks and the production build. Redis documents this [reconnection policy behavior](https://redis.io/docs/latest/develop/clients/nodejs/connect/).

The source change and tests are in the local `telegram` checkout:

```text
src/redis/index.ts
tests/redis-recovery.test.ts
```

The bot's fallback adapters hold state in memory during an outage. To avoid discarding that state through a restart, recovery used the existing client's `connect()` method in the running process. This procedure was first tested locally with the actual fallback adapter; the test retained its process and wrote both cached entries through its normal flush hook.

For the live recovery, the exact bot PID and command were verified before enabling Node's loopback-only diagnostic interface. Inspection found exactly one application Redis client, closed and not ready, with nine ready listeners. Calling `connect()` on that existing client returned `open=true`, `ready=true`, and `PING=PONG`. Its normal ready listeners remained attached. The application logged `[REDIS] client connected` at 19:57:04.898 UTC. The diagnostic listener was closed and its closure verified. The original bot process remained running. No Telegram message or moderation action was injected as a test.

The tested source fix has not been published or deployed as a new image. The current process recovered, but its original finite retry policy can fail again during another Redis outage. A reviewed deployment of the source fix is still needed for a lasting correction. Preserve the reconnect-before-restart sequence when deploying, so fallback state has an opportunity to flush through the running application's normal path.

## Application follow-up after 20:00 UTC

Redis recovery alone did not restore BAN ALL. Both BullMQ workers were stopped,
with Redis connections ready and no active jobs; about 18,760 jobs were queued.
The existing workers were resumed through their public `run()` method after
checking those states. The diagnostic listener was then closed. Existing queued
flows completed (observed examples: 662 successful and eight failed child jobs),
and progress messages advanced. No new moderation jobs were injected. The source
fix restarts unexpectedly rejected worker loops with a delay and respects pause,
shutdown and already-running workers.

The remaining sampled job failures were Telegram `400: not enough rights to
restrict/unrestrict chat member`. These require group administrator permissions;
storage repair cannot resolve them. At the final application check around 20:39 UTC, both queues had zero waiting
and zero active jobs. The executor retained 21,184 completed and 256 failed jobs;
the orchestrator retained 32 completed and zero failed jobs. The last 15 minutes
contained 16 completed flows and no logged errors or closed-client failures.
Counts are retention-dependent; sampled failures, not every failed job, were
checked for the administrator-permission error.

A separate PostgreSQL error rejected encrypted Unicode names. A valid 64-character
Chinese name produces 442 hexadecimal ciphertext characters, exceeding the old
192-character columns. Both `tg_users.first_name` and `last_name` were widened to
512 with a 500 ms lock timeout and five-second statement timeout. A temporary
copy of all 11,341 rows proved the change accepted the failing case without
altering existing data. The live transaction checked row count, row-content hash
and unchanged heap identity before commit. No name was truncated.

A fresh pre-change logical dump was verified: `postgres-before-name-widening.sql.gz`,
3,244,085 bytes, SHA256
`a62531cff839153c2f3a24917b3cd7a0b6248a8fceb927e073074a36e94b7963`.
A same-image rolling backend restart refreshed prepared statements after the DDL.
At 20:09 UTC the bot saved 1,141 previously blocked users. The backend PR records
the change in migration 0019; reapplying the widening is safe, but the normal
migration history still needs deployment. Do not run unrelated pending migrations
as an incident repair.

At 20:29 UTC the original node was Ready without memory or disk pressure, all
controller checks passed and all seven Longhorn volumes were healthy. Application
source changes and infrastructure PRs have not yet been deployed.

A proposed Bun SQL idle timeout was rejected after a local Bun 1.3.11 test killed
an active query at the configured timeout. It is absent from both production and
the PR. The PostgreSQL memory allocation cause remains unresolved.

## Remaining work, in priority order

1. Deploy the tested Telegram reconnect/worker recovery fixes and backend Redis recovery and name migration. Diagnose the backend's database connection lifetime. Investigate the memory-heavy PostgreSQL sessions and review the deployed Bun SQL connection options. Test connection recycling under load before deploying a fix. The recovery restart is a mitigation; the allocation cause remains unresolved. The backend also needs continued Redis reconnection after temporary outages.
2. Automate the verified multipath exclusion for future AKS nodes. Recheck device identities and configuration before applying it on a replacement. Do not blindly flush maps that have active users.
3. Establish verified off-node logical backups and restore exercises for PostgreSQL and MariaDB. Longhorn backups cover neither Azure Disk database volume. Verify the intended shared Redis dataset as well.
4. Align storage provisioning defaults with this one-node design: one replica, the configured backup target, and Retain where appropriate. Existing volume fixes do not change every future StorageClass provision. The Terraform Longhorn default already says one replica, but StorageClass parameters can override it.
5. Set resource budgets and health probes after measuring normal load. PostgreSQL currently lacks those protections. Review its deployment strategy before future rollouts so a single writable database volume cannot receive competing instances. Do not impose an arbitrary low database memory limit during recovery.
6. Resolve Telegram administrator permissions for failed moderation jobs. Verify the backlog continues to drain after deploying the worker recovery fix.
7. Plan Kubernetes and Longhorn maintenance separately. Observed versions were Kubernetes 1.29.13 and Longhorn 1.8.1. No upgrade was attempted during recovery.

One node can run the recovered workload, but it provides no node-level failover. All seven Longhorn volumes have their sole replica on the original node. Keep tested external backups and plan downtime for node maintenance. Adding replicas on the same node does not solve node failure.
